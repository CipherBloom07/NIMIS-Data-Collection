# ADR-001 — NIMIS Collect architecture and phased delivery

Status: **Accepted for development prototype; security and institutional integration decisions pending approval.**

## Assumptions and open questions

| Item | Working assumption | Open question / approval |
|---|---|---|
| Platform | React, TypeScript, Vite installable PWA | Does the Department require an Android Keystore-backed native wrapper for production? |
| Master record | One permanent scheme ID assigned by the main NIMIS server | Who owns and exposes the authoritative registry API? |
| Identity | Individual users, district/province-scoped on the server | Department identity provider and MFA policy? |
| Backend | Versioned REST API; PostgreSQL/PostGIS reference implementation if no main backend is available | Confirm existing NIMIS backend contract before deploying |
| Local storage | IndexedDB in prototype, no confidential data until encrypted-at-rest solution is approved | PWA-only storage cannot promise Android Keystore encryption |
| Evidence | Photo and GPS stored offline with local references | Media retention, consent, and allowed storage quotas |
| Verification | Capture → DIDO verify → PIDO review → national technical approval → administrator publish | Confirm delegation/substitute officer rules |
| Official branding | Provided Zimbabwe coat of arms and derived green/blue/gold palette | Approve official digital emblem asset before release |
| Form schema | Baseline questionnaire version 1; 10 additional forms are drafts | Department review of proposed dictionary |

## Why a PWA
The Windows Flutter installation failed during external Git/package fetches. A PWA is easier to run in VS Code, can use phone GPS and camera on HTTPS and can cache its interface for offline use. It reduces device setup and supports desktop/tablet workflows.

**Important constraints:** A browser PWA cannot, by itself, guarantee Android Keystore-backed encryption, secure biometric offline sign-in, long-running background synchronization after termination, permanent storage, or remote secure erasure. These are mandatory requirements in the provided brief. The production decision gate is to add a reviewed Android wrapper with native secure storage capabilities, or change to a suitable native technology before handling real Ministry data. We must not claim compliance without these capabilities.

## API first / data integrity
- Scheme master: one unique permanent ID, never assigned locally.
- Local draft: temporary UUID, assigned scheme ID optional.
- Submissions: append-only versions with per-operation client UUID and device/user identity.
- Recurring forms keyed by scheme, form, reporting period and optional season. Corrections link earlier versions rather than overwriting.
- Measurements: value, unit, observed_at, source and provenance; area concepts remain distinct.
- Verification events and attachment receipts are immutable.
- Synchronization is disabled until documented endpoints, security rules and schema have been validated.

## Build gates
1. Contract, data dictionary, conceptual schema: present for Department review.
2. Authentication and scoped reference downloads: NOT IMPLEMENTED.
3. Encrypted offline capture, photos, GPS boundary: PARTIAL PROTOTYPE; security gate open.
4. Push/pull, attachment resume, idempotency and conflicts: NOT IMPLEMENTED.
5. Ten recurring forms and review workflows: DICTIONARY DRAFT ONLY.
6. Security, accessibility, performance, localization: PARTIAL.
7. Pilot in different provinces: NOT STARTED.
